# Architecture (short version)

Full design document: [docs/assessment.md](assessment.md) (Farsi: [assessment.fa.md](assessment.fa.md)), sections 4–13. Online copy: https://claude.ai/artifact/RhHq7wisV2FZVNKjAdyALP

- **Bounded contexts → services.** Seven services are planned (reference, accounts, requests, cashflow, posting, reporting, documents). Each is built as an independent module (own projects, own database schema, own API contract, events through an outbox). For the pilot several modules may run in one process; splitting later is a deployment change (ADR 0001).
- **Layers per service:** Domain (rules, no dependencies) → Application (use cases, ports) → Infrastructure (PostgreSQL, messaging) → Api (HTTP). Enforced by `tests/Treasury.ArchitectureTests`.
- **Shared building blocks** (`src/BuildingBlocks`), the only code services share: `Treasury.BuildingBlocks.Domain` (aggregate root, domain exceptions with stable codes, `FiscalDate`, `PersianText`) and `Treasury.BuildingBlocks.Application` (`Result<T>`, `IUnitOfWork`, `IIdempotencyStore`, `ConcurrencyConflictException`, and `CommandRunner`: idempotency key + one transaction + rule violations turned into results). They know no service and no framework package; business rules never go there.
- **Data:** PostgreSQL 17, one database per client, one schema per service, transactional tables LIST-partitioned by fiscal year; closed years are frozen by trigger (ADR 0003).
- **Frontend:** Nuxt 4 shell + Vue micro-frontends via Module Federation 2.0, loaded at run time from manifests listed in `shell-config.json` (ADR 0004).
- **Several companies (ADR 0005, designed 19 Nov 2026, not built yet):** a company is the tenant and has its own database (no `company_id` columns); a client is one company or a group of companies; an installation is a client's server or the central hosted service. A small catalog per installation lists companies and their databases. Every request names one company, checked against the user's token; services reach the company's database through `ICompanyContext`; no command writes to two companies; combined group reports are read-only in `reporting-svc`. Until this is built, each service has one fixed connection string (one company per installation).
- **Phones and tablets (ADR 0006, designed 19 Nov 2026):** one web application for desktop, tablet and phone, installable on the home screen, online only; every new screen must work at 360 px and 768 px width.
- **Identity:** Keycloak (OpenID Connect). The API validates tokens when `Keycloak:Authority` is set; it refuses to start outside Development without it.

Built so far: the cashflow service's instrument and cheque-book model, its use cases and HTTP API, the PostgreSQL schema, the old-cheque migration tool, and the shell with the receipts micro-frontend (Phase 0); `reference-svc` with the simple Basic Information lists (currencies, country/province/city, bank names) and the Basic Information micro-frontend (Phase B, step 1). Receipts (14 Nov 2026): cashflow-svc's `Receipt` aggregate (cash, bank deposit, cheques and notes) asks accounts-svc about cash desks and bank accounts and reference-svc about payers' تفصیل, purpose groups and banks over HTTP (`Services:Accounts`, `Services:Reference`); a receipt of cheques is saved with its new instruments in one transaction (ADR 0002 amendment). The searchable list box `SearchSelect` is in the shared ui-kit (`@treasury/ui-kit/SearchSelect.vue`). Payment requests (15 Nov 2026): `requests-svc` (`src/Services/Requests`, schema `requests`, role `requests_svc`, port 5084, gateway `/api/requests/`) asks reference-svc about requesters, beneficiaries and purpose groups and accounts-svc about the account paid from; its micro-frontend is `frontend/remotes/requests` (`/remotes/requests/`). Opening or closing a fiscal year (`cashflow.open_fiscal_year`, `cashflow.close_fiscal_year`) also covers the `requests` partitions. The current status is in `README.md` (Farsi) and `README.en.md`.
