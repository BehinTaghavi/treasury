# Architecture (short version)

Full design document: [docs/assessment.md](assessment.md) (Farsi: [assessment.fa.md](assessment.fa.md)), sections 4–13. Online copy: https://claude.ai/artifact/RhHq7wisV2FZVNKjAdyALP

- **Bounded contexts → services.** Seven services are planned (reference, accounts, requests, cashflow, posting, reporting, documents). Each is built as an independent module (own projects, own database schema, own API contract, events through an outbox). For the pilot several modules may run in one process; splitting later is a deployment change (ADR 0001).
- **Layers per service:** Domain (rules, no dependencies) → Application (use cases, ports) → Infrastructure (PostgreSQL, messaging) → Api (HTTP). Enforced by `tests/Treasury.ArchitectureTests`.
- **Shared building blocks** (`src/BuildingBlocks`), the only code services share: `Treasury.BuildingBlocks.Domain` (aggregate root, domain exceptions with stable codes, `FiscalDate`, `PersianText`) and `Treasury.BuildingBlocks.Application` (`Result<T>`, `IUnitOfWork`, `IIdempotencyStore`, `ConcurrencyConflictException`, and `CommandRunner`: idempotency key + one transaction + rule violations turned into results). They know no service and no framework package; business rules never go there.
- **Data:** PostgreSQL 17, one database per client, one schema per service, transactional tables LIST-partitioned by fiscal year; closed years are frozen by trigger (ADR 0003).
- **Frontend:** Nuxt 4 shell + Vue micro-frontends via Module Federation 2.0, loaded at run time from manifests listed in `shell-config.json` (ADR 0004).
- **Identity:** Keycloak (OpenID Connect). The API validates tokens when `Keycloak:Authority` is set; it refuses to start outside Development without it.

Built so far: the cashflow service's instrument and cheque-book model, its use cases and HTTP API, the PostgreSQL schema, the old-cheque migration tool, and the shell with the receipts micro-frontend (Phase 0); `reference-svc` with the simple Basic Information lists (currencies, country/province/city, bank names) and the Basic Information micro-frontend (Phase B, step 1). Receipts (14 Nov 2026): cashflow-svc's `Receipt` aggregate (cash, bank deposit, cheques and notes) asks accounts-svc about cash desks and bank accounts and reference-svc about payers' تفصیل, purpose groups and banks over HTTP (`Services:Accounts`, `Services:Reference`); a receipt of cheques is saved with its new instruments in one transaction (ADR 0002 amendment). The searchable list box `SearchSelect` is in the shared ui-kit (`@treasury/ui-kit/SearchSelect.vue`). Payment requests (15 Nov 2026): `requests-svc` (`src/Services/Requests`, schema `requests`, role `requests_svc`, port 5084, gateway `/api/requests/`) asks reference-svc about requesters, beneficiaries and purpose groups and accounts-svc about the account paid from; its micro-frontend is `frontend/remotes/requests` (`/remotes/requests/`). Opening or closing a fiscal year (`cashflow.open_fiscal_year`, `cashflow.close_fiscal_year`) also covers the `requests` partitions. Company information (16 Nov 2026): reference-svc keeps the one `CompanyProfile` of the database (name, logo and the official details for printed forms, `/api/reference/company`); the Basic Information screen «اطلاعات شرکت» announces a change with the window event `treasury:company-changed` (`@treasury/ui-kit`, `company.ts`) and the shell's top bar reloads the name and logo, so the shell and the micro-frontend stay independent. Transfers between the company's own bank accounts (20 Nov 2026, owner's report no. 7): cashflow-svc's `BankTransfer` aggregate (electronic ways checked against `TransferLimits`, the company's own table; or a Sayad cheque that is one issued and one received `Instrument`) asks accounts-svc about both bank accounts and reference-svc about their banks' names; the issued cheque, its sheet and the transfer — and later the received cheque, and its collection — are saved in one transaction (ADR 0002 amendment). Since the owner's answer of 21 Nov 2026 every transfer names an approved payment request of the kind «نقل و انتقال بین بانک‌های شرکت»: cashflow-svc asks requests-svc for it and records the transfer on it as a payment over HTTP (`Services:Requests`), as an endorsed cheque does. The area «پرداخت‌ها» is the component `./Payments` of the receipts micro-frontend (the cashflow screens are one build) until payments to others are built. The current status is in `README.md` (Farsi) and `README.en.md`. Cheque transfer (19 Nov 2026, «ثبت انتقال (خرج چک)»): a payment request of that kind names a received cheque, so requests-svc asks cashflow-svc about it over HTTP (`Services:Cashflow`, `IReceivedChequeLookup`: is the cheque «ثبت صیادی شد» and transferable, its amount, number, due date and giver), while cashflow-svc still asks requests-svc when the transfer is recorded (`Services:Requests`). The two services call each other's API in different use cases; neither references the other's code or schema (ADR 0001), and only what was written on the cheque at the time is copied onto the request.
